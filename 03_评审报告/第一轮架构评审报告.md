## 一、指标→机制映射核对

| 基线指标 | 架构中对应机制 | 是否有支撑 |
|---|---|---|
| 并发≥50路 | Docker Compose FreeSWITCH + ESL，后端无明确限流机制 | ⚠️ P1：缺并发控制和资源隔离说明 |
| 端到端延迟≤2s | ASR→LLM→TTS 链路有设计，但缺超时控制和降级 | ⚠️ P1：超时/降级策略不明确 |
| 摘要≤5s | RabbitMQ 异步后处理，有 LLM 调用设计 | ✅ |
| 画布≥20节点 | X6 画布，无明确节点限制 | ✅ |
| 聚合查询≤500ms | ClickHouse 月分区设计 | ✅ |
| 单次任务≥1万号码 | 批量导入+RabbitMQ 异步消费 | ✅ |
| SSE推送≤1s | Spring SseEmitter | ✅ |
| 24h稳定 | 无健康检查/重连机制 | ⚠️ P1 |

## 三、问题清单

### P0（致命问题）
无。核心业务链路完整，技术选型可落地，无硬冲突。

### P1（需修正后通过）

| # | 问题 | 影响 | 修改建议 |
|---|---|---|---|
| P1-1 | 并发控制机制缺失：基线要求50路并发，但架构未说明如何限制单租户并发、如何排队 | 超并发时FreeSWITCH崩溃 | 增加：Redis 计数器做租户并发信号量，超过上限的号码排队等待 |
| P1-2 | 超时/降级策略不明确：LLM/ASR/TTS API 调用超时会导致对话卡死 | 用户等待超2s体验差 | 增加：LLM 超时5s降级为固定话术，ASR/TTS 超时重试1次后跳过该轮 |
| P1-3 | Redis 锁设计不完整：只写了 key，缺 Lua 脚本和防死锁 | 重复拨打或锁死 | 补充：SETNX+EXPIRE 原子操作，TTL 5分钟自动释放 |

### P2（后续优化）
| # | 问题 | 建议 |
|---|---|---|
| P2-1 | RabbitMQ exchange/queue 命名未定义 | 第二轮补充：exchange=call.event, queue=call.postprocess |
| P2-2 | 录音文件存储方案未说明 | 本地文件系统存储，路径写入ClickHouse |
| P2-3 | 前端路由/权限路由未设计 | 第二轮补充：JWT 前端路由守卫 |

## 四、结论

**修正后通过**。

P0 问题 0 个，P1 问题 3 个（并发控制、超时降级、Redis 锁细节）。这些都属于"设计不够细"而非"方向错误"，在第二轮定稿中补充即可，不影响整体架构方向。
